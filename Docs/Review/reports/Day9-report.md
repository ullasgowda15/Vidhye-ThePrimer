## The two design calls the builder flagged

**1. Vector retrieval only at story start and real branch points — endorse.**
This is §11.9 read literally rather than conveniently, and the implementation is honest about it: `beat_context_for` returns `""` at a non-branch point and `retrieve` skips the vector half on an empty context, so the gate is *structural* — there is no call site that can accidentally embed on every beat. The rule half (companion, fears, loves, recent salient) rides in every prompt, so the thing a beat must never lose is not gated on the thing that costs money. `is_branch_point` keys off `len(offered_labels) > 1`, which is the honest test of "did the story actually fork" rather than "was there a tap". Two notes, neither blocking: a counting beat that offers no cards is not a branch, so an adventure that is mostly counting refreshes the vector half only at beat 1 — correct by the cost argument, and worth remembering when someone later wonders why a mid-story memory did not surface. And the *bookkeeping* is not gated the way the embedding is (P2-1), so "we only retrieve at branches" is true of the provider call and not of the writes.

**2. Recall runs on local-hash (lexical) embeddings, so semantic quality is unverified — agree, and it is the day's largest unverified claim.**
What the test suite genuinely proves is the **plumbing**: the `vector` column round-trips, the HNSW index's `vector_cosine_ops` opclass matches the `CosineDistance` the query uses (a mismatch here builds an index nothing ever uses), ordering by distance works, and `_similarity = clamp(1 - d)` is the right transform for pgvector's cosine distance. What it cannot prove is **relevance**, because `LocalHashEmbeddingProvider` is lexical: "the right memory ranked first" currently means "the memory sharing the most words ranked first". Every retrieval assertion in `test_retrieval.py` is written against word overlap, and a real embedding model will reorder them — usually better, occasionally not, and nobody has looked. Two concrete consequences worth carrying into Day 10: (a) `RECENT_SALIENCE_FLOOR`, `WEIGHTS` and `MEMORY_RETRIEVAL_CANDIDATES=20` were tuned against a lexical signal and should be re-eyeballed once a real provider is in the loop; (b) `manage.py memories --recall "<context>"` already prints the ranked bundle with `sim/sal/rec` broken out, which is exactly the tool for that — it just needs a run with `OPENAI_API_KEY` set against the founder's own data before the day-two demo. Recommend that as the first thing on the next founder session.

## What's working well

- **The one property that had to hold, holds, and holds on the value.** `MemoryBundle.child_id` means "is this the right child's" is assertable on the object rather than only on the code that made it — and `mark_recalled` re-scopes its UPDATE to that `child_id` even though the ids already came from that child. Belt and braces on the single worst bug this product could ship.
- **The injection surface was retested where it moved to.** Day 7 proved the assembler labels what it is *given*; Day 9's red-team test plants the attack in a `Memory` row and drives it through retrieval, which is the surface that actually changed. That is the right instinct and it is rare.
- **The fallback is genuinely free.** First-meeting reuses Day 3's already-synthesised audio, so the answer to a provider outage, a schema failure, a refused greeting and a brand-new child is one code path that costs nothing and cannot itself fail. `greeting_calls=0` on the new-child path is the proof it is not merely re-deriving the same text expensively.
- **Degradation is named rather than hidden.** `bundle.degraded` distinguishes "the vector half was meant to run and could not" from "there was nothing to search", and the `exists()` check ahead of the embed call means day-one children cost no provider calls at all.
- **`_dedupe` merges rather than drops** the copy of a memory that both halves found, keeping the similarity the vector half measured. The docstring records that "keep the first" was tried and demoted the most relevant memory into the middle of the bundle — a real bug, fixed, and written down.
- **The retrieval query is scrubbed before it leaves for the embedding vendor** even though it never enters a prompt. That is §13.8 applied to a second vendor on a path the prompt guard never sees, and almost nobody thinks of it.
- **`manage.py memories --recall`** shows the whole bundle with the ranking broken out and deliberately bumps nothing — an inspection tool that changed recall strength would make the thing it measures drift every time you looked.

### P1 — should fix today

- [ ] **P1-1 — Nothing verifies the greeting references a real memory, so "welcome back" can be empty or invented.** `greeting.build` decides `kind=RETURNING` purely from `bundle.remembered` (does this child have stored rows), and then accepts whatever the model returns. Two failures I drove through the real code path:
  - Model returns `greeting="Rina! You came back. Come on, there is somewhere new to go today."`, `remembered=""` → ships `kind=returning`, and `ReturningGreeting.tsx:131` renders the heading **"Welcome back!"** with no memory under it. That is precisely the case `greeting.py`'s docstring says is *worse than the first-meeting hello* ("it makes a promise about being remembered and then does not keep it") — and the prompt itself invites it ("If the memories block holds nothing specific… return an empty `remembered`").
  - Model returns `remembered="Rina rode a purple whale to the moon."`, a memory that does not exist in the table → ships as a returning greeting, and the invented sentence is rendered on screen as what the companion remembers.

  `ReturningGreetingText.remembered`'s own docstring claims it "gives … a check that the greeting is about something in the bundle rather than something invented" — but no code performs that check. **Fix:** in `_generate`, after `guard_output`, require `remembered` to be non-empty *and* traceable to a bundle item (exact match, or a `salience.is_the_same_memory` gist match against `bundle.remembered` contents); on failure return `None` so the child gets the first-meeting hello. Add two tests, one per case above. This is criterion 2's actual guarantee, and today it rests on the model's goodwill.

- [ ] **P1-2 — `remembered` reaches the child's screen without passing the output guard.** `_generate` grades only the greeting text (`_as_gradeable(text)` wraps `narration=text`); `remembered` is returned unguarded, serialized by `ArrivalSerializer`, and rendered at `ReturningGreeting.tsx:148-155` on the child surface at `/welcome/:childId`. Proved by returning a benign `greeting` with `remembered="you were terrified and alone in the dark and nobody came for you"` — the greeting passed, and that sentence came back on `Greeting.remembered` untouched. It is derived from a scrubbed bundle so the *injection* risk is low, but §13.3's rule is about **text a child will hear or see**, and this is model output on the child's screen that no classifier read. The frontend comment calls the caption "for the adult in the room", which is not a property the screen has. **Fix:** grade both fields — simplest is `_as_gradeable(f"{text}\n{remembered}")` — or drop `remembered` from the child scene and keep it for the parent transparency log (§12.6) only. One test asserting an unsafe `remembered` triggers the fallback.

### P2 — improvements (non-blocking, log for later)

- [ ] **P2-1 — Recall bookkeeping records what was *retrieved*, not what was *said*, and that feeds its own ranking.** `mark_recalled(bundle)` stamps every stored item in the bundle. Because the rule-includes (stored fears, recent salient events) are in *every* bundle, they are stamped on every beat of every adventure: I measured an untouched fear row at **`recall_count=11` after 11 ordinary retrievals**, none of which mentioned it. Two consequences. (a) `greeting.py:198`'s comment — "bookkeeping on what was actually said, not on what was queried" — is not what the code does; the greeting stamps the whole bundle including memories the model never referenced. (b) `_recency` reads `last_recalled_at or created_at`, so anything that has ever been in a bundle sits at recency ≈ 1.0 permanently, and the recency signal saturates into rich-get-richer: what was retrieved keeps outranking what was not. Worth deciding deliberately before Day 10 builds on `recall_count`. Options: stamp only non-pinned items; or stamp only the ids the greeting actually referenced; or keep the write and drop `last_recalled_at` out of `_recency`.
- [ ] **P2-2 — "Always include active fears" is a rule in `must_include` but a score in `rank`.** `must_include`'s docstring says its order *is* the priority the budget truncates against ("who the companion is, what frightens the child, what they love, what happened lately"), but `rank` re-sorts the pinned block by `-score`, and stored rows are scored by the weighted sum. Constructed case: a fear row (salience 0.6) ranks **below** a recent event (salience 0.95) that the vector half also matched, and at a tight budget the fear is the one dropped. Profile fears currently sort ahead of profile interests only by an alphabetical accident ("is afraid of" < "loves"). The arithmetic says this cannot bite at the shipped numbers — worst-case pinned block with the shipped caps (`MAX_SEED_LENGTH=60`, `CONTENT_CHARS=240`, 3+3+3+3+1 items) is ≈ 590 tokens against an 800 budget, and I could only force a drop (2 of 6 fears kept) by writing 236-character seeds straight to the model, which the serializer would reject. But that safety is an unasserted arithmetic coincidence between four constants in three files. **Fix:** either give the pinned block a stable class order independent of score, or add the one test that pins the invariant (`worst-case must_include tokens < MEMORY_RETRIEVAL_TOKEN_BUDGET`) so a future cap change fails loudly instead of quietly dropping a fear.
- [ ] **P2-3 — HNSW + a `child` filter is a scale risk nothing here can see yet.** `_nearest` runs `ORDER BY CosineDistance LIMIT 20` over `memory` filtered to one child. With a single shared HNSW index, pgvector walks the graph globally and filters after; at production scale (many families, one table) a child with a handful of memories can come back with fewer than `limit` neighbours — or none — while the planner still thinks the index is the right choice. Invisible today (test DBs hold a handful of children) and invisible in staging. Worth an explicit decision before the memory table gets big: iterative index scans, a partial/partitioned index, or an explicit row-count threshold below which the query goes sequential.
- [ ] **P2-4 — The headline greeting unit test can pass without a memory reaching the model.** `test_it_greets_by_name_and_references_a_seeded_memory` asserts `"stepping stones" in result.text or "Sparkle" in result.text` — and `ScriptedAIProvider.greeting` *always* appends "Come on — {companion} has somewhere new to show you today", so the `Sparkle` branch is satisfied unconditionally. The same `or` appears in `test_two_children_get_different_correct_greetings` (its anti-bleed assertions are sound; the positive one is not). The strict form does exist in `tests/test_greeting_api.py:70`, which is why criterion 7 passes — but the test named for criterion 2 should be the strict one. Drop the `or`, or assert on `result.remembered`.
- [ ] **P2-5 — `estimate_tokens` is documented as conservative and is slightly permissive.** `CHARS_PER_TOKEN = 4` with the comment that an estimate running under the truth "would silently spend the budget it exists to enforce" — but English averages a shade *under* four characters per token, so `len/4` runs low; `ITEM_OVERHEAD_TOKENS = 6` (vs ~3 real tokens of `- (type) ` framing) is what actually buys the margin back. Net conservative in practice, and academic at 90–494 of 800, but the constant and its rationale currently disagree. Also worth noting the budget bounds the *bundle*, not the rendered layer — the DATA fence preamble (~55 tokens) sits outside it.
- [ ] **P2-6 — The greeting ignores the input guard's `Decision`.** `_generate` reads `guarded.get("memory")` and never looks at `guarded[safety.GUARD_KEY]`; the orchestrator, by contrast, branches on it for §13.10 escalation. Scrubbing is the right mitigation for retrieved memories and the incident *is* written inside `guard_input`, so nothing is currently missed — but a future guard action that means "do not generate from this" would be silently ignored on this path. One line, or one comment saying why not.

## Scope & risk notes

- **Scope discipline: clean.** No learning engine, no objective selector, no interest-graph world selection. `objective_for` is still the Day-4 placeholder; the `interest` items in the bundle are onboarding seeds rendered as facts, not a weighted graph. `seed_memories` is gone and its two responsibilities (interests, fears) were folded into `must_include` rather than duplicated — the only Day-3 behaviour change is that a child with no seeds now gets a bundle containing their companion instead of an empty list, which is correct and is pinned by a rewritten test.
- **Architecture fidelity: good.** Hybrid = vector + rules + recency/salience weighting, ranked and truncated to a token budget, injected as labeled DATA through the existing `memory_bundle` layer — §11.9 and §19.4 line by line, with the assembler and `guard_input` reused rather than bypassed. Nothing in `greeting.py` assembles its own prompt.
- **Cost posture:** the new endpoint is throttled at `30/hour` on its own scope (not sharing `companion_read`), the client asks once per arrival with `staleTime: Infinity` and `retry: false`, TTS is cached on `(voice, text)`, and the vector half is gated to branch points. The one unbounded-ish cost left is that `mark_recalled` writes on every beat (P2-1) — cheap, but it is a write per beat that nobody asked for.
- **Frontend:** no spinner (a companion walking over), no error (a failed request renders the companion and the ★ anyway, so a child is never stranded), heading driven by `kind` off the wire. `/welcome/:childId` sits outside the parent guards next to `/meet`, and `ChildHome`'s star now routes through it. 102 frontend tests pass, including the returning/first-meeting/failed-request three.

## What I could not verify
- **Semantic retrieval quality against a real embedding provider** — no `OPENAI_API_KEY` in this environment; `local-hash` is lexical. Structure (column, opclass/distance match, ordering, degradation) verified; relevance not. See Design call 2.
- **Real-provider greeting text** — `ScriptedAIProvider` quotes a memory out of the assembled prompt, which is what makes the assertions meaningful, but the warmth, length and reciprocity of a live Claude greeting is a founder-eyeball item (`make smoke-story` / a keyed `manage.py memories --recall`).
- **Latency with a network embedding call** — 14.3 ms median is local Postgres plus a local hash. The provider round trip is the term that will decide whether §11.9's "at story start and key branches" needs prefetching.
- **The scale behaviour of HNSW under a `child` filter** (P2-3) — cannot be observed at test-database size.
