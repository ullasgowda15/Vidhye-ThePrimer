## The ~50s time-to-first-beat, honestly

**The plumbing is not the problem.** Everything that could turn a slow generation into a *worse-feeling* slow generation has been done right: headers reach the client in 50 ms, the open comment is on the wire before any model is called, the narration is emitted the instant it validates rather than waiting on media, the two media calls overlap, the POST deliberately does *not* generate the beat, and the whole wait is dressed as the companion thinking rather than as a spinner. There is no redundant call and no accidental serialisation anywhere on the path.

**The felt latency is nonetheless worse than the build summary suggests, and almost all of it is the model.** Measured today against the configured provider (`AI_PROVIDER_ORDER=openrouter,anthropic`, `AI_BEAT_MODEL=google/gemma-4-26b-a4b-it:free`):

| Stage | Where it runs | Measured |
|---|---|---|
| Plan call | inside `POST /adventures`, blocking | **65.1s**, then **15.0s** on a repeat; isolated `build_plan` calls: **15.8s** and **7.4s** |
| Beat call | inside the stream, before the `beat` frame | **26.4s** (`gen_ms=26375`) |
| Illustration + voice | concurrent, after the beat frame | **10.1s** wall (voice 6.0s, image 10.1s) |
| **Star tap → first word on screen** | plan + beat, sequential | **~35s best case, ~91s worst observed** |

So the honest number is not 50 seconds; it is *somewhere between 35 and 90*, and it moves by a factor of two between consecutive runs. The spread — 7.4s to 65.1s for the *same* call — is the signature of a free-tier queue, not of anything in this repo. Two things follow, and it is worth keeping them apart:

- **Model speed / provider tier (the large majority).** `:free` OpenRouter models are queued behind paid traffic. PRODUCT §16.1 names Claude as the primary and the router already supports it with a one-line env change; the single highest-leverage latency fix available today is `AI_PROVIDER_ORDER=anthropic,openrouter`, and it is a config change, not code. Nothing should be re-architected before that measurement is taken.
- **Code-side structure (the remainder, and it is architectural rather than wasteful).** Two model calls sit in strict sequence before the child hears a word, because beat 1 needs its stage line from the plan. Neither is streamed at the token level — structured output means the full JSON must arrive before it can be validated — so the narration appears all at once rather than growing. And `MAX_OUTPUT_TOKENS = 8000` is generous for a five-line plan. None of these are bugs; they are the honest cost of "validate before the child sees it", and I would not trade that away. But they do mean the floor is *plan latency + beat latency*, and if the target is a few seconds, the plan is the piece to attack first (cache it per child per day, generate it during companion creation, or make it a cheaper/smaller call).

**One thing that is genuinely masked and should not be.** The child-facing wait is covered by an animation with no upper bound. If the plan or the beat never returns, `StoryPage` shows a thinking companion forever and nothing ever nudges. That is correct for Day 4 (§13 says never an error) and it is Day 7's problem to give the silence an ending — but it means latency regressions are invisible from the child's side by design, so the `story.beat gen_ms=` log line is the only place anyone will ever see them. Worth watching.

## What's working well

- **The streaming claim survived every way I tried to break it.** A two-second `curl` that got exactly the 8-byte open frame and nothing else, `transfer-encoding: chunked` with no `content-length`, and per-frame arrival times 6 and 10 seconds apart. This is the single thing the review brief calls "the #1 thing to get wrong", and it is right — including `X-Accel-Buffering: no` for the nginx that is not there yet, and the deliberate *omission* of `Connection: keep-alive` with a comment explaining that it is the server's business under ASGI.
- **`thread_sensitive=False` is load-bearing and the code knows it.** The docstring on `_offload` states that the default would make `asyncio.gather` run two provider calls sequentially *while still looking concurrent* — which is exactly the bug that would have passed every test and quietly doubled every beat's latency. The `overlap_ms` log line exists so that regression is visible rather than inferred.
- **Validation sits between the model and the database, not between the database and the child.** `Beat.model_validate` runs before `Beat.objects.create`, so there is no state in which a malformed beat is persisted-but-unrendered. The repair lives on the router rather than in the beat path, so it cannot be forgotten by the next caller, and it is capped at one by construction rather than by a retry counter someone could raise.
- **The replay path is right, and it is right for the stated reason.** `ensure_first_beat` checks before it generates, uses `seq=1` explicitly rather than "next free", and is backed by a `UniqueConstraint(adventure, seq)` plus an `IntegrityError` catch that adopts the winner. The comment explaining why "next" would be wrong — two streams producing a beat 1 and a beat 2, so the child is told the opening and then told a second opening — is the kind of reasoning that stops a future refactor from undoing it. It works: I watched a second open replay in 0.09s.
- **The cookie has one owner.** `accounts/cookies.py` sets all four attributes in one function and every view routes through it, so the failure mode it names — `HttpOnly` on login and not on rotation, i.e. a refresh token that becomes script-readable fifteen minutes after sign-in — is structurally impossible rather than remembered. `move_to_cookie` strips `refresh` from the body in the same call that sets the cookie, so a view cannot do half the job.
- **The CORS fix landed with the cookie, not after it.** The two are a pair — `SameSite=Lax` as the primary control, a scoped allow-list as defence in depth — and `dev.py` says so in prose next to the regex. The anchored regexes were checked against three near-miss origins and held.
- **Errors are logged with the adventure and shown to nobody.** `stream_failed`, `media_failed`, `plan_failed` and `beat_race_lost` all carry the adventure id at `error`/`info`, and `dev.py` grew a `LOGGING` block specifically so `apps.*` INFO reaches the console — the observability of this pipeline is the product, and before this day it went nowhere under `make run`.

### P1 — should fix

- [ ] **A hard refresh mid-story starts a brand-new adventure, and the code comment says it does not.** `useBeginAdventure` is a `useQuery` keyed on `['adventure', childId]` with `staleTime: Infinity` (`queries.ts:194-205`), which correctly dedupes within one mount — but React Query's cache is memory-only (`grep` for `localStorage`/`sessionStorage`/`persistQueryClient` across `frontend/src` → **no hits outside a test assertion**), so a reload loses the adventure id and `StoryPage` POSTs a new one. Two live POSTs fifteen seconds apart for the same child returned `f409f1e8-…` and `368d5ecd-…` — different adventures, different plans. The founder's own dev database has **seven adventures for one child ("Spidey") between 07:58 and 08:21, six of them with a distinct opening beat**: a garden with a map, a garden with a big green leaf, a jungle, a playroom, a bedroom, a playground. Each reload costs a plan call, a beat call, an illustration and a TTS call (§22.4), and drops the child into a different story. The comment at `queries.ts:190-192` asserts the opposite — *"The backend replays an adventure's existing beat rather than regenerating it, so a reload lands the child back in the same story either way"* — which is true of the backend and false of the product, and will keep the gap invisible to whoever reads it next. This is why criterion 8 is 🟡: its written clause passes, its founder test does not. **Fix:** give the child surface a way to name the adventure it is resuming — a `GET /children/{id}/adventures/current` (or `POST` returning the in-progress adventure instead of creating a second one) is the smallest change, and it makes the backend's replay path reachable for the first time. Then correct the comment.

- [ ] **A client that disconnects mid-generation still pays for the beat and leaves it with no picture and no voice.** Proven live: a `curl -N` killed after 2 seconds produced `story.beat … gen_ms=26375` twenty-four seconds later — the offloaded thread runs to completion and persists the beat even though the coroutine awaiting it was cancelled — and no `story.media.timing` lines at all, because `stream_media` never ran. The founder's database shows the same shape three times over: of six persisted beats, **one has neither an illustration nor a voice, one has an illustration but no voice, and one has neither**. That beat self-heals if the *same* adventure is reopened (`first_beat_state` returns `None` URLs and the media stages run) — but P1-1 guarantees the same adventure is never reopened, so in practice these are permanent, paid-for orphans. In dev it is worse than occasional: `StrictMode` is on (`main.tsx:11`) and `StoryPage`'s stream effect aborts and re-runs on every mount, so **every development page load opens the stream twice on a beatless adventure and pays for two beat generations**, one of which loses the `(adventure, seq)` race and is discarded. **Fix:** either finish the media stages independently of the response lifecycle (a Celery task keyed on the beat, which the media pipeline is already shaped for), or make the beat generation itself cancellable so a vanished client stops costing money. Either way, add the "beat exists but has no media" case to the stream's replay branch as a deliberate repair rather than an accident of `if not (image_url and audio_url)`.

## Scope & risk notes

- **Front-running: none.** No choice endpoint (`grep choices backend/apps/story/urls.py` → nothing), no consequence beats, no memory retrieval, no embeddings, no safety hardening beyond `safety_status='unchecked'` written honestly on every beat. `Choice` is defined and never written, exactly as the brief asks. `prev_choice` is plumbed through `build_beat_context` / `create_beat` / `generate_beat` but is `None` at every call site — a seam with a named shape, which is what Day 5 needs. The learning directive is the declared placeholder (`PLACEHOLDER_OBJECTIVE`) and says so.
- **Architecture fidelity: good.** ASGI-only stream with no WSGI fallback, as instructed. DRF for the POST, plain async Django for the stream, and the file explains why each is what it is.
