## The workflow (unchanged)

Per day: hand a fresh Claude Code session `docs/Build/DayN.md` (build) → new session with `docs/Review/DayN.md` (review → writes `docs/Review/reports/DayN-report.md`) → if issues, a `docs/Build/DayN-fix.md` closes them → founder manual-tests → commit + push → CI green → next day. Build and review are always separate sessions; the reviewer never edits code. ## Day 14 watch-items for the review + manual test

- **`create_adventure` now opens the `PlaySession` *before* generating the plan**, which it did not before. The reason is §22.4: a plan is a full LLM call, cost is measured per session, and a plan generated before its sitting existed is a real charge with nowhere to file it — so the adventure that costs most to start would be the one the dashboard could say least about. The consequence to check: if anything between the session insert and the plan raises a *non-*`AIError` (`build_plan` catches `AIError` and falls back by design), we now leave an empty `PlaySession` row where before we left none. That row would extend a Day-13 sitting via `sitting_started_at`. Judged acceptable because the path was already returning a 500, but it is the one ordering change in the day and deserves a second opinion.
- **`beat.delivered` is five rows per adventure and will be the largest table in the product.** It earns its volume — it is the denominator of both safety-ops numbers (§13.11, §22.5), and "twelve incidents" means nothing without "in nine thousand beats". §17.4 says this table should be *partitioned by time*; it is not, and `drain_events --prune` is the only thing that bounds it. Worth revisiting before real volume.
- **The greeting and the companion's assets are traced but deliberately *unattributed* to a session.** Both happen before any `PlaySession` exists — the arrival scene, and onboarding — so they show on the dashboard under `operation=greeting` / `character` / `narration` with a null session and land in `unattributed_usd`. That is semantically right (they are not session costs) and it means `cost/session` is a *story* cost, not a whole-relationship cost. Not a bug; a reviewer should know which question the headline number answers. Attributing them to a *child* (rather than a session) is a one-line refinement left undone.
- **`metrics._first_stories()` and `_play_dates()` load two event names into memory and group in Python.** Deliberate at alpha scale and flagged in the module docstring; the first thing to rewrite as window functions when the numbers get real.
- **The scripted provider and the offline media renderers are priced at zero, honestly**, so every cost aggregate in CI reads `$0.0000` with `unpriced_spans 0`. `test_a_paid_route_produces_a_non_zero_cost_per_session` prices the scripted route absurdly for one test so the arithmetic is genuinely exercised — but the first real number is a manual-test result, not a CI one.
- **`events.track` raises on an unknown name only when `DEBUG`.** In production it logs and drops, because rule 1 is that telemetry never costs a child a beat. The trade: a mistyped name in a code path only production reaches is a metric that reads zero and a line in a log. The closed `Event.NAMES` set is what makes that nearly unreachable.
- **The warehouse export is the one place a delete does not reach.** Rows already written to NDJSON persist after `DELETE /account`. They carry no name, no birthdate and no free text — only opaque ids and scalar props — so they are de-identified rather than retained, which is a weaker promise than "gone" and is said in those words in `drain_events`' docstring. ## Day 12: what landed

- **`apps/analytics/models.py`** — one table, `SessionReport`. Stored rather than computed on read for three reasons, in order: a report is a claim about one afternoon and recomputing it next month against a changed catalog would quietly rewrite what a parent was told; §17.5 prunes the beats it was derived from; and the highlight costs a model call. `session` is nullable (SET_NULL) while `session_key` is not — the URL key and the idempotency gate both have to survive a retention job clearing the FK. **The weekly report is deliberately not a table** — a stored weekly row is a second thing that can disagree with the sessions it summarises, plus a second idempotency problem, to save a cheap query.

## Day 12 watch-items for the review + manual test

- **The one thing a reviewer should try to break is the grounding gate.** Everything else on this surface degrades safely; a fabricated sentence about a real child does not. `is_grounded` is generous by design (substring matching, phrases *and* their words), and the failure direction chosen was "occasionally passes a vague sentence" over "rejects good writing for using a synonym". A reviewer who disagrees with that trade should say so — it is the judgement call of the day.
- **The scripted provider now answers `SessionHighlight`** (`conftest.py::ScriptedAIProvider.highlight`), reading the digest and quoting something the child actually did. That means CI exercises the *model* path end to end rather than only the monkeypatched one — but it also means the grounding gate is being tested against a provider that is trying to pass it. What a real model does with the prompt is a manual-test question.
- **Two sittings in a row practise different objectives**, by design (§10.3 interleaves domains). It caught two of my own tests out. Any test about how *one* objective moved across a week has to pin the code rather than play twice — `test_reports.py::_snapshot_last_week` is the helper and says why.

- **`_key_choice` takes the *last* branching beat, not the first.** A five-beat arc opens with a decision that sets direction and closes with one the story built toward; the second is the one a child tells their parent about. Defensible either way.
- **Consent is required on every dashboard read** (`require_consent`), consistent with every other child-data endpoint. ## Day 10 fix pass: what changed, and what to feel for
