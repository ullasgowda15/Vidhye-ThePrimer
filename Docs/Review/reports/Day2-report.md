## What's working well
- **The consent gate is real, and its *ordering* is the thing that was got right.** `ConsentRecord.child` is nullable precisely so consent can be granted before any child exists, and the frontend test is named *"records consent before asking for anything about the child"*. That is COPPA's actual requirement — consent precedes collection — rather than a checkbox collected alongside the child's name.
- **Consent evidence is server-observed, not client-supplied.** `parent`, `ip`, `granted_at`, and `evidence_ref` are all set in `perform_create` from the request, and `evidence_ref` is read-only in the serializer. A consent record whose evidence the client could dictate would not be evidence, and the code says so in a comment.
- **Ownership is defended in both places it can leak.** `IsParentOwner` covers detail routes; `ParentScopedQuerysetMixin` covers list routes — and the docstring explains *why* detail routes deliberately resolve unscoped (so an ownership bug shows up as a distinguishable 403 rather than being indistinguishable from a deleted row). That is a considered decision, documented, not an oversight.
- **The cascade test in the repo walks the live schema.** `test_children.py` asserts the delete guarantee by enumerating FKs from the database rather than listing tables by hand, so a model added on Day 8 is covered the day it lands. I re-derived the same list independently and got the same three tables.
- **Tokens are deliberately kept out of persistent storage,** with the trade-off written down (`store/auth.ts`): a hard reload signs the parent out, and the endgame (httpOnly `SameSite` refresh cookie) is named and scoped to one file. There is a test called *"keeps tokens out of persistent storage"* pinning it. The in-flight-refresh singleton also correctly prevents a dashboard's parallel 401s from each spending the rotating refresh token — a bug that would show up only under concurrency.
- **The prompt assembler is built as a safety component, not plumbing.** Pure, deterministic, no clock, no network; `memory` and `turn` are hard-mapped to `DATA` by the assembler itself so a future call site *cannot* promote a memory to an instruction; and layers are keyed then emitted through `LAYER_ORDER` so an undocumented layer raises `KeyError` instead of silently appearing.
- **Scope was held.** No companion endpoint, no story loop, no billing, and the assembler is genuinely unwired — `grep` finds no caller outside its own tests, exactly as the brief required.

Exploitability is low — API auth is a bearer header rather than a cookie, and DRF's `SessionAuthentication` enforces CSRF on unsafe methods — but the Day-2 review brief explicitly asks for CORS scoped to the dev origin, and `base.py` already computes exactly that list. `prod.py` is correctly scoped from env. - [ ] **The cascade guarantee is enforced by Django, not by the database.** All three FKs report `delete_rule: NO ACTION` in `information_schema` — standard Django, which implements `on_delete=CASCADE` in Python. But "delete my child's data" is a legal promise: if a future admin action, data migration, or ops script ever deletes via raw SQL, it will error rather than cascade. Worth a line in the runbook when §17.5's deletion flow is built properly.
- [ ] **`POST /auth/logout` requires a live access token** (`permission_classes = [IsAuthenticated]`). The one live gap is the dev CORS override (P2) and the short local key (P1).
- **COPPA fidelity (§13.7).** Consent is verifiable-*lite* but genuinely recorded: type, method, server timestamp, server-observed IP, and an evidence reference, with `revoked_at` for withdrawal and an index on `(parent, consent_type)`. `ConsentView` is create-only by design — a change of mind is a new record or a revocation, never an edit of the old one, which is what makes the table an audit trail. `REQUIRED_CONSENT_TYPE` is env-driven so bumping the version forces everyone to re-consent. The disclosure text itself lives in the onboarding UI; I read it as plain-language, though I did not evaluate it as legal copy.
- **Schema fidelity (§17.2).** `ConsentRecord` matches the Build §4.1 stub field-for-field, with one deliberate improvement: the serializer exposes it as `child_ref` and scopes that field's queryset to `Child.objects.filter(parent=request.user)` in `__init__`, so a parent cannot mint a consent record pointing at another family's child. `Child` matches §17.2 including the derived `age`/`age_band`.
