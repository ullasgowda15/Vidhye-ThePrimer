## The learning beat, quoted (criterion 3's evidence)

A five-year-old at `count_to_5` mastery 0.50 → selector picks `count_to_5` at difficulty 0.60 → `COUNT_LADDER` → five things. Beat 2 of 5, verbatim from the database:

> **Narration:** *"Because you chose Follow the sparkling river, the river goes quiet, and 5 little frogs are sitting along the fallen log in the sun."*
> **The companion asks:** *"How many can you see?"*
> — `interaction.type: count`, `expected: 5`, `choices: []` (the number pad, not cards)
> — `learning: {objective_id: "count_to_5", difficulty: 0.6, skill_evidence_key: "count_riverbank"}`

There is a story on the screen and a curriculum in the row underneath it, and they share no words. Nothing in the narration, the spoken prompt or the client frame names counting as a skill, a difficulty, an objective or a result. The child's own interest (frogs) supplies the countable things, which is the mechanism working exactly as §8.10 describes: the *plot* contains the objective rather than carrying it. The engine's log line for the same beat — `learning.objective_selected … objective=count_to_5 difficulty=0.60 mastery=0.50 due=0 candidates=6` — is the entire visible difference between this and a storybook.

## The two flagged judgment calls

**1. Two learning asks per adventure (beats 2 and E−1) — endorse, with a caveat about short stories.**
The argument in `learning_seqs` is correct and I would not want it reversed: **one ask cannot adapt.** §10.4 requires difficulty to move within a sitting on live evidence, and with a single ask the adaptation could only ever surface in tomorrow's adventure — which is spacing, not adaptation. Two, with ordinary story between them, is genuinely the smallest arrangement that satisfies §10.4, and the code refuses to go past two ("A five-beat story with four asks in it is a worksheet with pictures"). The caveat is the floor: `estimated_beats` clamps to **5–7**, and at 5 the seqs are `(2, 4)` — beat 1 opens, beat 5 is the warm close, so **two of the three answerable beats are learning asks**, with a single decision point between them. My probe hit exactly that shape, and because `count_to_5` clamps at five things, *both asks were the identical ask*: count five frogs, walk, count five frogs. A real model would dress the second scene differently, but the demand it is written from is byte-identical. That is the ratio the code itself calls "the invisibility", sitting at its worst allowed value. Not a blocker — a 5-beat story with two counting moments is still a story — but it deserves a real-model playtest before it is called settled, and gating the second ask to `total_beats >= 6` would cost nothing (see P2-1).

**2. Interest fit matches skill words only, never scenery — endorse the decision, but the term is inert in practice.**
Matching on scenery was tried and was actively harmful: `name_colours` seeded with "the green frog" as an illustration handed a frog-loving five-year-old vocabulary instead of counting **on their first ever adventure**, and the stopword gap before that let "the sea" match every description containing "the". Both are kept as regression tests, and the seed migration now carries an explicit rule ("Descriptions name the skill and never the scenery"). That is the right call and well defended. But it leaves the term firing on almost nothing. I dumped every objective's token set:

```
count_to_3   -> count each group loud number one saying small three visible
count_to_5   -> count five losing partway track visible without
more_fewer   -> fewer group has look more say side two which
count_to_10  -> count each how keeping know last many number one said ten there visible
name_colours -> colour describe named point use whatever word
size_words   -> deep enormou huge narrow scale size tiny understand use word
feeling_words-> character curiou delighted feeling how name proud worried
```

Every token is skill vocabulary. A parent typing what a child actually loves — dinosaurs, space, trains, frogs, boats, princesses — scores **0.0 against all seven**, and `INTEREST_WEIGHT` (0.25) never enters the arithmetic. Only "colours", "numbers" or "feelings" fire, which are skills a parent might name but rarely will. So §10.3's third balance term is nominal today: the selector is really two terms and two penalties. The module says so honestly ("Deliberately weak, and worth saying why rather than dressing it up… the real version of this reads the interest graph (§11.7), which is Day 11"), and the seam is in the right place. Recorded as **P1-4** so it is not mistaken for a working feature between now and Day 11, not because the design is wrong.

## What's working well

- **The tag is stamped, not trusted.** `learning_tag_for` overwrites the model's `objective_id` and `difficulty` and keeps only `skill_evidence_key` — the one field a writer is actually in a position to know. §8.10's tag exists to verify the objective was exercised, and a tag self-reported by the thing being verified verifies nothing; more sharply, `difficulty` is read straight back as the anchor for the mastery update, so a model's guess at it would corrupt the skill model directly. Proven by injecting `objective_id: "banana_studies", difficulty: 0.99` into a provider response and watching `count_to_5 / 0.6` come out.
- **The objective is chosen before the plan.** `create_adventure` runs `select_objective` first and feeds the choice into the planning prompt, so the skeleton *contains* the river with five stepping stones instead of a beat having to invent a reason for them mid-story. `test_the_plan_is_built_around_the_objective` asserts `"Primary objective: count_to_3"` and `"countable at a glance"` reach the plan call.
- **Degradation is quiet and correct in every direction I could find.** No catalog → adventure with `primary_objective_id=None` and a beat that still narrates. Objective deleted mid-adventure → `demand_for_adventure` returns None and the prompt says *"No learning objective is set… keep the beat playful and let the story lead"*. Safe fallback beat → `objective_id: "none"`, so a degraded sitting produces **less** evidence rather than false evidence. Evidence for an objective no longer in the catalog is logged and dropped, never used to invent a row. A missing objective is never a missing beat.
- **`is_due` refuses the obvious shortcut.** A never-practised objective is **not** due, because "due" means a schedule came round and a brand-new objective has no schedule. Conflating them would make every untouched row permanently overdue and drown out the review that spacing exists to schedule. That is a small decision with a large blast radius and it was got right.
- **The model is interpretable, as §10.2 requires and Day 12 will need.** Four numbers, each with a sentence a parent would accept. `uncertainty` is documented as "a learning rate wearing an honest name, not a posterior variance, and calling it one would be a claim the arithmetic underneath does not support" — exactly the right posture for a number a parent is going to be shown.
- **`admin.py` makes `LearningProgress` read-only in every field that matters**, so the founder manual test ("did counting mastery move?") means something: nothing but a child's play could have moved it.

### P1 — should fix
- **P1-1 — Mastery is anchored to the difficulty *requested*, not the one *delivered*; `COUNT_CEILING` breaks the anchor.** `demand_for` clamps `quantity` to the objective's own ceiling but leaves `Demand.difficulty` at the requested value, and that value is what `learning_tag_for` stamps and what `observation()` reads back. Measured:

  | objective | stamped difficulty | things actually asked for | observation on a clean win |
  |---|---|---|---|
  | `count_to_5` | 0.55 → 0.65 → 0.75 → 0.85 | **5, 5, 5, 5** | 0.75 → 0.85 → 0.95 → 1.00 |
  | `count_to_3` | 0.50 → 0.70 → 0.90 | **3, 3, 3** | 0.70 → 0.90 → 1.00 |

  The child counts the same three frogs every time and the estimate climbs to 1.00 because a number that changed nothing about the ask kept rising. This is precisely the property the day set out to guarantee — "counting two frogs correctly cannot push a child's estimate to mastery" is true at the bottom of the ladder and false in the clamped region at the top. It is reachable in a **first sitting**: my probe stamped 0.75 on beat 4 while the ask was still five frogs, because beat 2 went well and `adapt` stretched. Consequences are real but bounded: `mastery` is what Day 12 shows a parent, and it is what `PREREQUISITE_MASTERY = 0.6` gates the next link on — inflation here promotes children up the counting chain faster than their evidence warrants. **Fix (small, in the module's own idiom):** after clamping `quantity`, clamp `difficulty` down to the top of the band that yields that quantity, so `Demand.difficulty` always describes the ask actually made. Add the invariant as a test: *for any objective and any difficulty, two demands with equal `quantity`/`gap`/`novel_word` must carry equal `difficulty`.* `test_an_objective_never_asks_for_more_than_its_own_ceiling` already covers the quantity half and reasons about exactly this hazard in the other direction ("the mastery update would then credit ten things to an objective about three") — the mirror case was missed.
- **P1-2 — `update_from_session`'s gate is per *session*, so the second adventure of a sitting would be silently dropped.** The stamp is `PlaySession.learning_updated_at`, and the task returns `"already"` on any later delivery. Today one session holds one adventure (`create_adventure` opens a session per adventure; no caller passes `session=`), so this is **not reachable now** — but §17.2 permits several, `engine.update_from_adventures` is written for several, and the moment a sitting spans two stories the first `end` stamps the session and the second adventure's evidence is never folded in. Unlike the parallel `consolidated_at` case in `apps/memory` — which loses *attribution* and documents the limit in `_first_adventure_id` — this loses the evidence entirely, and `tasks.py` asserts idempotency without naming the boundary. **Fix:** either gate per adventure, or at minimum record the limitation in the task docstring next to the `learning_updated_at` argument so the day the session cap lands, this is found by reading rather than by a mastery number that stopped moving.
- **P1-3 — Nothing checks real model output for lesson leakage.** Invisibility is enforced entirely at the prompt layer, and the assertions that prove it run against `ScriptedAIProvider` — whose `learning_narration` was *written* to avoid lesson words ("Deliberately free of the words a lesson would use"). So `test_a_reader_of_the_beat_sees_a_story` proves the pipeline injects no lesson language; it cannot prove a model emits none. Meanwhile the system layer does carry `Primary objective: count_to_5` and `Target difficulty: 0.6 (0 easiest, 1 hardest)` — the two strings most likely to be echoed back into narration — and there is no post-generation check for either. This codebase already has the pattern: `_log_consequence_misattribution` and `_log_choice_distinctness` are warn-only quality probes over generated beats. **Fix:** add a sibling that warns when `beat.narration` or `interaction.prompt_audio` contains the objective code, the difficulty string, or any of `lesson/practise/practice/quiz/test/score/correct answer`. Cheap, in-pattern, and it turns the day's headline guarantee into something observable in production rather than only in fixtures.
- **P1-4 — The interest-fit term is inert for realistic interests.** See judgment call 2. `INTEREST_WEIGHT = 0.25` scores 0.0 for every interest a parent is likely to enter, so §10.3's third balance term does not currently participate in selection. The decision behind it is right; the status should be recorded rather than assumed working. **Fix:** carry it into Day 11 as the named landing site for the interest graph (`interest_fit` is already documented as that seam), and until then don't count interest fit as an operative term when tuning the other weights.
